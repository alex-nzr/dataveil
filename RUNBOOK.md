# Runbook: анонимизация Bitrix24

Документ описывает два рабочих сценария:

1. Анонимизация уже развернутой копии портала Bitrix24.
2. Анонимизация SQL-бэкапа или Bitrix `.tar.gz` архива через временную БД.

Не запускайте DataVeil по production-базе. Работайте только с копией портала, тестовой БД или временной БД, созданной из бэкапа.

## Общая подготовка

1. Создайте рабочий `configuration.yaml` на основе `configuration_example.yaml`.
2. Оставьте активным только один источник подключения:
   - `database.source: bitrix_settings` для развернутой копии портала;
   - `database.source: mysql` для прямого подключения к подготовленной БД.
3. Проверьте, что rules покрывают нужные сущности: пользователей, лиды, контакты, компании, сделки, реквизиты, адреса и смарт-процессы.
4. Для смарт-процессов проверьте таблицы `b_crm_dynamic_items_*` и чувствительные `UF_*` поля конкретного портала.

Проверка конфигурации:

```bash
php dataveil.phar test:configuration configuration.yaml
php dataveil.phar test:db-connection configuration.yaml
```

## Сценарий 1: анонимизация развернутой копии портала

Используйте этот сценарий, если Bitrix24 уже развернут в тестовой среде или на отдельной копии, и DataVeil должен изменить БД этой копии напрямую.

### 1. Подготовить копию

1. Создайте копию портала и БД.
2. Убедитесь, что это не production.
3. Проверьте путь к `bitrix/.settings.php` или прямые MySQL-параметры в `configuration.yaml`.
4. Если используется `bitrix_settings`, конфиг обычно выглядит так:

```yaml
database:
    source: "bitrix_settings"
    bitrix:
        settings_file: "/path/to/bitrix/.settings.php"
        connection_name: "default"
```

### 2. Выполнить dry-run

```bash
php dataveil.phar anonymize configuration.yaml --dry-run
```

Dry-run не меняет данные. Он проверяет таблицы, колонки, стратегии, consistency groups и показывает количество строк, которые будут затронуты.

Если dry-run показывает ошибки по таблицам или колонкам, сначала исправьте конфиг. Реальный запуск до этого выполнять нельзя.

### 3. Выполнить анонимизацию

```bash
php dataveil.phar anonymize configuration.yaml
```

Команда меняет данные в БД, указанной в `configuration.yaml`. Поэтому перед запуском ещё раз проверьте вывод `test:db-connection` и убедитесь, что выбрана копия, а не production.

### 4. Проверить портал после запуска

1. Откройте тестовый портал.
2. Проверьте вход в административную часть.
3. Проверьте пользователей, лиды, контакты, компании, сделки и смарт-процессы.
4. Проверьте, что телефоны/email заменены согласованно в карточках и активностях.
5. Проверьте, что связи не сломаны: сделки связаны с контактами/компаниями, UF-ссылки открывают связанные элементы.

## Сценарий 2: анонимизация бэкапа через временную БД

Используйте этот сценарий, если нужно обработать файл бэкапа, не изменяя развернутый портал.

### 1. Подготовить исходный бэкап

1. Создайте отдельный бэкап БД штатным механизмом Bitrix24 или подготовьте SQL-дамп другим контролируемым способом.
2. Создайте отдельный бэкап файлов портала, если он нужен для восстановления тестовой копии.
3. Передавайте в DataVeil только бэкап БД. Полный бэкап портала с файлами подавать на вход не нужно: приложение рассчитано на SQL-дамп/архив БД, а полный файловый архив содержит тысячи файлов, не требует анонимизации на этом этапе и сильно замедлит обработку.
4. Убедитесь, что исходный файл БД не находится в production-директории, где его может перезаписать другой процесс.
5. Не меняйте исходный файл вручную. DataVeil читает его только как источник.

Поддерживаемые форматы:
- `.sql` - одиночный SQL-дамп;
- `.tar.gz` - архив БД Bitrix24 с основным SQL и `*_after_connect.sql`.

Если окружение не содержит `mysql` и `mysqldump` в `PATH`, подготовьте явные пути к бинарникам:

```bash
--mysql-bin "/usr/bin/mysql"
--mysqldump-bin "/usr/bin/mysqldump"
```

Для backup-режима пользователь БД из активного источника `database.source` должен иметь права создать и удалить временную БД, импортировать дамп, обновить данные и экспортировать результат. Если таких прав нет, используйте режим `--reuse-temp-db` с заранее созданной технической БД. Для безопасной эксплуатации лучше использовать отдельный технический MySQL/MariaDB-сервер или отдельного пользователя, которому разрешена работа только с временными базами с префиксом `dataveil_tmp_`.

Если пользователю нельзя выдавать `CREATE DATABASE` и `DROP DATABASE`, администратор MySQL должен заранее создать отдельную БД с именем вида `dataveil_tmp_<project>` и выдать пользователю права только на эту БД. В `configuration.yaml` можно указать эту же БД в `database.mysql.database`, а при запуске передать её же в `--temp-db`, но обязательно добавить `--reuse-temp-db`.

### 2. Выполнить dry-run бэкапа

```bash
php dataveil.phar backup:anonymize configuration.yaml \
    --input backup.tar.gz \
    --temp-db dataveil_tmp_project_check \
    --dry-run
```

Dry-run импортирует дамп во временную БД, запускает preflight и удаляет временную БД после проверки. Анонимизация и экспорт результата не выполняются.

Если временная БД уже существует, команда завершится ошибкой и не удалит эту БД.

Если используется заранее созданная БД без прав на создание/удаление баз, dry-run выполняется так:

```bash
php dataveil.phar backup:anonymize configuration.yaml \
    --input backup.tar.gz \
    --temp-db dataveil_tmp_project_check \
    --reuse-temp-db \
    --dry-run
```

В этом режиме DataVeil очищает содержимое `dataveil_tmp_project_check`, импортирует туда дамп, выполняет preflight и после завершения снова очищает содержимое. Сама БД не удаляется.

### 3. Выполнить анонимизацию бэкапа

```bash
php dataveil.phar backup:anonymize configuration.yaml \
    --input backup.tar.gz \
    --output backup.anonymized.tar.gz \
    --temp-db dataveil_tmp_project_run
```

Для заранее созданной временной БД без прав `CREATE DATABASE`/`DROP DATABASE` добавьте `--reuse-temp-db`:

```bash
php dataveil.phar backup:anonymize configuration.yaml \
    --input backup.tar.gz \
    --output backup.anonymized.tar.gz \
    --temp-db dataveil_tmp_project_run \
    --reuse-temp-db
```

Если `--output` не указан, DataVeil построит имя автоматически, добавив `.anonymized` перед датой Bitrix-дампа.

После успешного запуска:
- исходный backup остаётся без изменений;
- временная БД удаляется, если не используется `--reuse-temp-db`;
- с `--reuse-temp-db` удаляется не БД, а её содержимое;
- результат записывается в `--output`.

Перед упаковкой результата DataVeil нормализует SQL-дамп после `mysqldump`: удаляет служебные строки с восстановлением переменных `@saved_cs_client` и `@OLD_*`, которые могут мешать восстановлению через штатный механизм Bitrix.

### 4. Проверить anonymized-бэкап

1. Убедитесь, что output-файл создан и имеет ожидаемый размер.
2. Для `.tar.gz` проверьте состав архива:

```bash
tar -tf backup.anonymized.tar.gz
```

Внутри должны быть переименованные файлы:

```text
bitrix/backup/<name>.anonymized_<timestamp>_sql_<suffix>.sql
bitrix/backup/<name>.anonymized_<timestamp>_sql_<suffix>_after_connect.sql
```

3. Выполните dry-run уже по anonymized-архиву:

```bash
php dataveil.phar backup:anonymize configuration.yaml \
    --input backup.anonymized.tar.gz \
    --temp-db dataveil_tmp_project_verify \
    --dry-run
```

Это проверяет, что новый архив импортируется и соответствует правилам конфигурации.

### 5. Восстановить anonymized-бэкап в тестовую среду

1. Используйте только тестовую или временную среду.
2. Не восстанавливайте anonymized-бэкап поверх production.
3. После восстановления проверьте вход в Bitrix24, CRM-карточки, списки, сделки, контакты, компании и смарт-процессы.
4. Проверьте, что телефоны/email заменены согласованно в карточках и активностях.
5. Проверьте, что связи не сломаны: сделки связаны с контактами/компаниями, UF-ссылки открывают связанные элементы.

## Что делать при ошибке

- Если ошибка возникла до создания временной БД, удалять ничего не нужно.
- Если ошибка возникла после создания временной БД и `--keep-temp` не указан, DataVeil удалит только БД, созданную текущим запуском.
- Если ошибка возникла из-за того, что временная БД уже существует, DataVeil не удаляет эту БД.
- Если использован `--reuse-temp-db`, DataVeil не удаляет саму БД. Без `--keep-temp` он очищает её содержимое после завершения или ошибки.
- Если использован `--keep-temp`, временную БД нужно удалить вручную после анализа:

```sql
DROP DATABASE dataveil_tmp_project_run;
```

В режиме `--reuse-temp-db` обычно не нужно удалять саму БД. Если `--keep-temp` был включён для анализа, после проверки очистите содержимое вручную или запустите следующую команду с `--reuse-temp-db`: DataVeil очистит БД перед новым импортом.

## Минимальный чек-лист перед передачей

Для прямой анонимизации портала:
- `test:configuration` проходит.
- `test:db-connection` показывает ожидаемую копию БД.
- `anonymize --dry-run` проходит без ошибок.
- После `anonymize` тестовый портал открывается, CRM-сущности и связи проверены.

Для анонимизации бэкапа:
- `test:configuration` проходит.
- `test:db-connection` показывает ожидаемую техническую БД/сервер.
- Если используется заранее созданная БД, команда запускается с `--reuse-temp-db`, а имя БД начинается с `dataveil_tmp_`.
- `backup:anonymize --dry-run` проходит на исходном бэкапе.
- Полный `backup:anonymize` создаёт anonymized-файл.
- Anonymized-файл проходит повторный `backup:anonymize --dry-run`.
- Восстановление anonymized-файла проверено в тестовой среде.
